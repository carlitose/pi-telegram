## Type and evidence
Bug analysis and feature spec. In the installed `@llblab/pi-telegram` 0.50.1 runtime, redacted `tmp/telegram/logs.jsonl` repeatedly records HTTP 400 `message thread not found` on outbound messages, while the diagnostic snapshot marks `topic-state` and `target-bindings` suspect. This proves failed outbound delivery, not that every inbound failure has the same cause. A read-only comparison of the redacted stale-target event against the current active binding confirms that they refer to **different Thread targets in the same chat**; the stored binding remains open for the other target. Repeated outbound errors may therefore belong to an already-captured old turn; they do not prove the new binding is stale. The source checkout is 0.51.6 at `b47720b231c5af43769d540fc57281d2f850bec1`; the installed 0.50.1 tag already contains the same exact-target/no-replay recovery regression in `tests/bus-api.test.ts`. `lib/sync.ts` contains stale-target invalidation, and `lib/threads.ts` optimistically reuses a target until an actual send fails. A fresh input on the current binding still needs live verification.

Pi's current public `ui_prompt_start`/`ui_prompt_end` events expose only `kind` and optional `title`. The installed host's extension runner wraps local `select`, `confirm`, `input`, `editor`, and `custom` dialogs and emits notification-only events; they contain neither choices/message nor a response port. The documented RPC `extension_ui_request`/`extension_ui_response` protocol operates in RPC mode, not as a TUI extension API. The bridge already observes these events for activity and typing (`lib/lifecycle.ts`, `lib/bindings.ts`, `docs/activity.md`). These facts are a technical gate, not permission to inject terminal input, read private runtime state, or treat an ordinary Telegram message as an answer to a blocked dialog.

## Goal
A paired owner can receive and answer supported Pi dialogs from the assigned Telegram chat/Thread while the original Pi session remains the owner. Send one ordinary, non-silent Telegram notification when human input becomes necessary; routine activity must not create repeated attention alerts. Telegram clients/users control the actual notification sound, which the bot cannot guarantee.

## Non-goals
- No remote terminal, arbitrary command forwarding, headless Pi instance, or replacement of Pi's TUI.
- No generic serialization of `custom()` components. `pi-code.question` is eligible only through its separate typed, question-owned event contract; arbitrary custom UI remains local.
- No clearing or rewriting Telegram ownership, journals, bindings, or pending input to repair a stale target.
- No promise that a Telegram notification arrives during transport outage or that a device plays a sound.

## Target behavior and invariants
1. A stale/deleted Thread observed through a proven exact-target Telegram error is invalidated under current profile/leader authority. The next supported reconnect/reconciliation provisions or restores a **new proven target** without replaying an uncertain send or discarding queued work. No answer or alert goes to a different Thread, profile, or user. If the current checkout already satisfies this, retain a regression and mark the slice no-op rather than adding a redundant recovery path.
2. Pi publishes an official opt-in dialog contract for `select`, `confirm`, `input`, and `editor` with one stable request ID, session generation, origin, full safe prompt/options, cancellation/deadline, and a typed single-settlement response API. A successful remote response settles **one** dialog result. When the remote responder declines, delivery fails, or its bounded wait expires, Pi opens its normal local dialog; the TUI is not concurrently active while a remote answer is pending. The owner of the Pi API must define the exact cancellation, expiry, and compatibility semantics. Existing notification-only events remain observational. Until this API exists and is validated, remote dialog completion is blocked.
3. The Telegram bridge forwards only eligible dialogs for the **current connected session and authorized target**. A paired owner's button/text reply resolves the exact live request once; a stale, duplicate, unpaired, other-Thread, timed-out, disconnected, or replaced-session reply has no effect. Dangerous or irreversible operations retain the original Pi confirmation semantics; an alert or button alone is not approval. Ordinary Telegram prompts never silently become dialog answers.
4. At most one attention message per newly opened eligible dialog, not on each polling tick, model token, tool event, or repeated lifecycle update. Routine delivery remains visible per the existing companion contract but should use Telegram's silent-send option where supported *only* under an explicit notification policy that preserves existing defaults until configured. The dialog alert is non-silent; Telegram's client settings determine the actual sound. No alert is sent merely because a tool or agent is busy, or if no dialog can be answered remotely.
5. On delivery failure, preserve the local Pi dialog and report the failure diagnostically. Never declare it answerable in Telegram without confirmed delivery to its exact target. An unsupported custom component requires the local Pi UI rather than a nonfunctional reply control.
6. The distinct `pi-code.question` tool can offer a typed single-/multi-select, free-text or cancel request via the public in-process extension event bus. Only after a synchronous one-claim handoff for the current authorized target may the bridge handle it. Represent choices in a numbered reply-to-message prompt: one index for single-select, comma-separated indices (or `none`) for multi-select, `/text <answer>` for numeric free text, and `/cancel`. An exact-target reply attempt resets a configured question idle timeout via `touch()`. A claim is provisional until delivery is confirmed; preserve the local TUI overlay when unclaimed or delivery fails, and reject late or duplicate remote replies. This does not generalize to arbitrary `custom()` UI or waive ticket 02's host API for ordinary Pi dialogs.

## Verification and open gates
Unit tests: stale-target evidence/recovery, idempotent dialog settlement, rejection of wrong identity, cancellation and expiry, notification deduplication. Integration tests: real Pi public dialog lifecycle with TUI and Telegram responders, classic plus leader/follower and replacement; packaging build/typecheck/focused tests. Live tests on a disposable Telegram Thread and device: inbound/outbound after a deleted Thread, each supported dialog, `pi-code.question` single-/multi-select and free text after its separate contract is integrated, alert only while waiting, device-controlled sound, local fallback and offline transport. No live behavior is claimed from simulations. The Pi host proposal [earendil-works/pi#10123](https://github.com/earendil-works/pi/pull/10123) was **auto-closed**, not reviewed or merged: host `CONTRIBUTING.md` requires prior maintainer `lgtm` approval and green `npm run check` plus `./test.sh`. The host patch remains in `carlitose/pi` branch `feat/remote-ui-prompt` and is not released upstream. An explicitly authorized experimental local fork installation exists on disk, but the running Pi/leader combination and dialog behavior are not thereby verified. The bridge uses a structurally typed adapter while the installed Pi peer lacks that event. Forks `carlitose/pi` and `carlitose/pi-telegram` exist, but upstream PR approval/merges belong to their maintainers. The host's targeted dialog/runner tests pass; the full monorepo check stops on unrelated hydrated model-catalog test references to removed `kimi-k2.6`. Bridge reply unit tests/typecheck/build and an isolated fork-package mock integration pass, not full cross-repository or live dialog acceptance. A user-confirmed message reached disposable Thread E and an E-originated Telegram input appeared in its Pi TUI; a separate cross-Thread agent-turn routing request failed after text delivery, so neither result proves dialog settlement. Origin provenance, optional quiet-routine notification policy, classic/leader/follower real-process coverage, a compatible published host version, fresh mobile input on the current binding, and device notification behavior remain open gates. Do not install either candidate as a working remote-dialog package on these tests alone.
